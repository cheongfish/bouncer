# 온톨로지 검색 논의와 다음 실험 계획

2026-10-15, develop `711be703`. 앞선 결과는 [`case-study.md`](case-study.md)에 있다.
이 문서는 그 뒤에 이어진 논의(온톨로지 필드, 손익, 포트폴리오 용도)와 다음 작업을 기록한다.

## 결론 먼저

1. 플러그인 코어에는 온톨로지 검색을 넣지 않는다. 줄일 수 있는 몫(과거 문서 검색)이 세션 도구 결과의 약 4%다.
2. 포트폴리오용 독립 실험으로는 진행한다. 범위는 "과거 결정 질의에 답하는 비용을 줄이는가"로 한정한다.
3. 실험은 두 조건을 지킨다.
   - 검색 단계 지표와 전체 세션 지표를 함께 보고한다.
   - 정답 집합을 온톨로지와 독립된 출처로 만든다.
4. 플러그인 토큰 최적화는 별도 과제로 다룬다. 실제 비용은 coordinator의 CLI 호출과 플러그인 문서 읽기에 몰려 있다.

## 필요했던 필드

컨텍스트 문서 632개(epic 52, blueprint 201, explain 182, tasks 60)의 채움률이다.

| 필드·섹션 | 채움률 | 상태 |
| --- | --- | --- |
| blueprint `## Contract` | 192/201 | 거의 다 채워짐. 자유 문장 |
| explain의 task `#### Touch` | 391개 항목 | 거의 다 채워짐. `경로 — 설명` 자유 형식 |
| explain `task_commits` | 103/182 (57%) | 절반만 채워짐 |
| tasks `affected_paths` | 60개 | task 문서가 finalize 뒤 explain으로 접혀 대부분 사라짐 |
| `supersedes` | 실제 값 2개 | 사실상 빈 필드 |
| `depends_on` | 3개 | 사실상 빈 필드 |

인과 질의에 필요했던 관계는 네 종류다.

1. **문서와 코드 연결:** 모든 closed BP의 `task_commits`. finalize에서 필수였어야 했다.
2. **타입이 있는 엔티티:** blueprint frontmatter의 `defines`·`modifies`. CLI 명령·플래그, 규칙 항목, G/S 코드, 거절 사유, 원장 kind, 설정 키 같은 것들이다. 지금은 Contract 본문의 백틱에만 있다.
3. **결정 간 부분 수정:** `amends: [{bp, entity}]`. BP는 이전 결정을 대체하기보다 일부를 고치므로 `supersedes`만으로는 늘 비게 된다.
4. **Touch 항목의 역할:** `mirrors`(예: `agents/*.md`와 `.codex/agents/*.toml`), `verifies`(성공 기준과 테스트), `documents`(기능과 규칙 문서).

`mirrors`처럼 확실한 동기화 의무는 그래프 간선보다 validate 검사로 두는 편이 싸다.

## 손익

[`context-search-share.py`](context-search-share.py)로 이 저장소의 Claude Code 세션 653개(도구 호출 11,749회)를 쟀다.

| 분류 | 호출 | 도구 결과 크기 |
| --- | --- | --- |
| 현재 BP 문서 읽기·쓰기 | 23.8% | 19.9% |
| 과거 문서 검색 | 6.5% | 3.8% |
| 그 외(코드, CLI, 플러그인) | 69.6% | 76.2% |

벤치마크 `v088007-ledger-004-bouncer-full-{1,2}`(`benchmarks/aggregate/workflow-breakdown.py`)에서도
컨텍스트 문서 읽기는 도구 호출의 7%였고 대부분 현재 BP 문서였다.

- 이득 상한: 과거 문서 검색을 완벽히 대체해도 약 4%. 에이전트가 결과를 다시 확인하면 그보다 작다.
- 확인된 비용: 그래프 질의 규칙을 읽는 비용으로 토큰 6~12% 증가(실험 1).
- 작성 비용: 필드 출력 자체는 작다. 필수 필드를 게이트로 강제할 때 생기는 실패·수정 반복이 크다.
- 품질 위험: 에이전트가 쓴 관계가 빠지거나 틀리면, 그래프를 믿고 grep을 생략한 쪽이 grep보다 나빠진다.

판단이 바뀌는 조건:
- 과거 문서 검색 비중이 15~20%를 넘는다.
- 작성 비용이 0이다. 에이전트가 쓰지 않고 CLI가 기존 문서에서 결정적으로 색인을 만든다.
- 목표가 토큰이 아니라 정확성(연관 규칙·미러 파일 누락 방지)이다.

측정 한계:
- 분류는 경로·명령 문자열 판정이라 근사치다.
- 바이트는 토큰과 비례하지만 같지 않다.
- 세션에 분석 세션이 섞여 과거 문서 검색 비중이 부풀려졌을 수 있다.

## 실험 설계 (포트폴리오용)

| 항목 | 내용 |
| --- | --- |
| 가설(사전 등록) | B가 정답 재현율을 A 대비 0.05 이상 잃지 않으면서, 질의당 토큰을 30% 이상 줄인다 |
| 질문 | 과거 결정 질의 30~50개. 예: "`model-invalid`를 정의하거나 수정한 BP는?", "`rules/subagent-model.md`를 바꾸면 영향받는 결정과 파일은?" |
| 조건 | A: grep·파일 읽기만 / B: 온톨로지 질의 CLI, 필요하면 grep |
| 지표 | 질의당 토큰, 도구 호출 수, 정답 대비 정밀도·재현율 |
| 반복 | 질문당 조건별 3회. 같은 질문끼리 짝지은 부트스트랩 95% 신뢰구간 |
| 보고 | 검색 단계 감소율과 전체 세션 기준 환산(상한 약 4%)을 함께 적는다 |

온톨로지 구축 방식은 기존 문서에서 결정적으로 추출하는 오프라인 색인이다. 문서 형식은 바꾸지 않는다.
- 노드: epic·BP·task, 엔티티(Contract 백틱 토큰을 종류별로 분류), 파일
- 관계: BP–엔티티(`mentions`, Contract 위치), BP–파일(Touch, `task_commits` diff), BP–BP(같은 엔티티·파일 공유)

순환 평가 금지: 정답은 색인을 만든 Contract 텍스트에서 뽑지 않는다. 출처 후보는 두 가지다.
- git 이력: 엔티티 문자열이 diff에 나타난 커밋과 그 커밋의 BP
- 직접 라벨링: 질문과 정답을 사람이 작성. 설득력이 가장 높지만 시간이 든다

예상: 토큰 감소는 입증될 가능성이 높다. 관문은 재현율이다. 백틱 없이 문장으로만 적힌 결정은 색인에서 빠진다.
