# 사례 연구: 그래프·온톨로지로 plan 토큰을 줄일 수 있는가

2026-10-14 ~ 2026-10-15, Bouncer 1.5.9 (develop `711be703`)

## 요약

- 질문: 코드 그래프나 컨텍스트 문서 frontmatter로 만든 관계 그래프(온톨로지)가 "이 파일을 바꾸면 무엇이 같이 바뀌는가"를
  알려줘서 plan 단계의 탐색 토큰을 줄일 수 있는가.
- 측정 두 가지:
  1. Graphify 원본 질의로 Task 변경 파일 추정(BP 9~30개, 에이전트 실행)
  2. frontmatter `task_commits`로 이은 co-change 이력으로 소스 외 변경 파일 예측(BP 56개, 결정적 백테스트)
- 결과:
  - 소스 파일은 Graphify로 잘 찾는다(recall 0.92). 그러나 `grep` 기준선과의 차이는 유의하지 않았고, 토큰은 6~12% 더 들었다.
  - 기존 `bouncer graph-suggest`는 BP 12개, Task 34개 전부에서 후보를 내지 못했다(F1 0).
  - co-change 이력은 F1에서 `grep`을 유의하게 이겼지만(+0.10), 재현율이 0.38이라 탐색을 대체하지 못한다.
- 결정:
  - `graph-suggest`를 제거하고 원본 Graphify 질의로 전환한다(epic 100).
  - 온톨로지 검색은 만들지 않는다. 측정된 이득이 유지 비용과 규칙 문서 읽기 비용을 넘지 못한다.

## 배경

Bouncer는 plan 단계에서 epic·blueprint·task 문서를 쓰고, 각 task가 바꿀 파일(`affected_paths`)을 정한다.
이 경로를 정하려고 에이전트가 저장소를 넓게 읽는 비용이 plan 토큰의 상당 부분이라는 가정에서 출발했다.
컨텍스트 문서 632개는 이미 공통 frontmatter(`type`, `tags`, `bouncer.epic_id`, `task_commits`, `affected_paths`,
`supersedes` 등)를 갖고 있어, 이를 관계 그래프로 올리면 영향 범위 질의가 가능하다는 아이디어가 있었다.

## 실험 1: Graphify 질의

상세는 [`graphify-query-investigation-2026-10-14.md`](graphify-query-investigation-2026-10-14.md).

- 입력: explain 문서의 Task 설명에서 경로·줄 번호를 가린 문장
- 정답: Task 커밋의 실제 변경 파일
- 스냅샷: BP 첫 커밋의 부모 트리로 그래프를 만들어 미래 정보 누출을 막음
- 조건: 규칙 적용 Graphify(A), 자연어 질의(B), 후보 생성기(C), `grep`만 쓰는 기준선(D)

| 관찰 | 값 |
| --- | --- |
| 소스 recall (Graphify) | 0.92 |
| A − D F1 차이 | +0.055, 95% CI [−0.009, +0.127] (BP 9개) |
| 에이전트 총 토큰 (그래프 조건 대비 기준선) | +6 ~ 12% |
| `graph-suggest` F1 | 0 (BP 12개, Task 34개) |
| 테스트·규칙·에이전트·스킬 문서 | 그래프에 없거나 연결이 끊겨 찾지 못함 |

Graphify가 못 찾는 소스 외 파일이 남은 문제였다. 실험 2는 이 구멍을 이력 데이터로 메울 수 있는지 봤다.

## 실험 2: frontmatter 이력 기반 co-change 백테스트

설계는 [`README.md`](README.md). 요점만 적는다.

- frontmatter 관계 중 실제로 채워진 것은 `task_commits`뿐이었다(문서 103개, 풀리는 커밋 255개).
  `supersedes`는 실제 값 2개, `depends_on`은 3개라 문서 간 영향은 처음부터 잴 수 없었다.
- seed는 BP가 바꾼 소스 파일, 정답은 소스 외 변경 파일 802개(BP 시작 시점에 있던 파일 730개 → recall 상한 0.91)

| 조건 | 정밀도 | 재현율 | F1 | BP당 후보 |
| --- | --- | --- | --- | --- |
| G: 파일 stem `grep` | 0.20 | **0.70** | 0.25 | 65.7 |
| C: co-change (지지도 2 이상, 신뢰도 0.2 이상) | 0.36 | 0.41 | **0.35** | 15.0 |
| CK: co-change 상위 8개 | **0.43** | 0.32 | 0.32 | 7.6 |
| R: `grep` 후보를 co-change로 재정렬, 상위 15개 | 0.37 | 0.42 | 0.34 | 12.8 |
| RU: 합집합 재정렬, 상위 15개 | 0.34 | 0.44 | 0.33 | 14.6 |

(macro 평균, BP 56개)

- C − G F1: +0.097, 95% CI [+0.046, +0.148]. 이력 데이터는 grep보다 정밀하다.
- RU − C: −0.011, 95% CI [−0.040, +0.019]. grep과 섞어도 나아지지 않는다.
- 범주별 재현율(C): 테스트 54%, 규칙 24%, 스킬 25%, 에이전트 31%, 참조 문서 12%.
  grep은 같은 범주에서 52~79%를 찾는다.

해석: co-change는 "후보 15개 중 5~6개가 맞는" 힌트 수준이다. 에이전트는 결국 나머지를 직접 확인해야 하고,
실험 1에서 본 것처럼 힌트를 읽는 규칙 비용이 더해지면 토큰이 오히려 늘 수 있다.

## 결정과 이유

| 선택지 | 결정 | 이유 |
| --- | --- | --- |
| `graph-suggest` 유지 | 제거 | 전 표본에서 F1 0 |
| 원본 Graphify 질의 | 소스 탐색에만 사용 | recall은 높으나 토큰 절감 미입증. 정확한 심볼 질의를 묶어 한 번에 실행하는 규칙으로 한정 |
| 온톨로지(타입 있는 엔티티·관계 그래프) | 만들지 않음 | 재료 관계가 비어 있고, 이력만으로 얻는 F1 0.35를 넘는다는 근거가 없음. 추출·스키마 유지 비용이 생김 |
| co-change 힌트 | 보류 | 토큰 A/B에서 절감이 확인될 때만 고려 |

다음에 잴 것은 plan 토큰이 실제로 어디서 쓰이는지다. 이전 재측정에서는 plan 비용 증가의 원인이 문서 검색이 아니라
context-review 형식을 파고드는 데 있었다. 그 비중이 크면 그래프보다 그쪽을 먼저 줄이는 게 맞다.

## 한계

- 실험 2의 seed는 정답 소스 파일이다. 실제로는 소스 탐색 오차가 더해진다.
- `grep` 기준선은 파일 stem만 찾는 단순한 방식이다. 에이전트의 판단이 섞인 grep은 더 정밀하다(실험 1의 D).
- 학습 데이터에는 Bouncer 밖의 커밋도 섞여 있고, BP 사이 커밋이 겹칠 수 있다.
- 토큰은 실험 1에서만 쟀다. 실험 2는 예측 품질만 잰다.
- 단일 저장소(Bouncer 자체)의 이력이다. 이력이 짧은 저장소에서는 co-change 신호가 더 약하다.
