# Bouncer의 가치와 브랜딩 방향

이 문서는 Bouncer의 사용 가치, SDD 지향점, Superpowers와의 경쟁, 병렬 task 실행에 관한 논의를 정리한다. 브랜딩 제안과 평가이며, 제품 로드맵이나 성능 우위가 확정됐다는 뜻은 아니다.

## 1. 사용 가치에 대한 평가

초기 평가는 Bouncer를 에이전트의 범위 이탈과 검증 누락을 줄이는 도구로 보았다. 이 기준에서는 핵심 통제 기능에 가치가 있지만, 전체 워크플로를 모든 개발 작업의 기본으로 도입할 근거는 부족하다고 판단했다.

실질적인 장점은 다음과 같다.

- 검증 명령의 실제 실행 기록을 확인한다.
- 검증 이후 소스가 바뀌면 기존 증거로 커밋하는 것을 거절한다.
- 승인 범위 밖의 파일이 커밋에 섞이는 것을 검사한다.
- 구현·검증·리뷰의 역할을 분리한다.

반면 도입 비용과 제품 완성도에 관한 우려도 확인했다.

- 경량 경로에도 계획 문서, 검증, 리뷰, 설명, 퀴즈가 따른다.
- 설치 문서는 `release` 브랜치 사용을 요구하지만 README의 설치 명령에는 해당 지정이 없다.
- 설치 문서상 Claude Code·Cursor·Codex·Antigravity의 설치 smoke는 모두 미검증이다.
- 마감 퀴즈는 오답이어도 진행할 수 있지만 무응답이면 마감을 막는다. 교육적 효용과 필수 절차로서의 필요성은 구분해야 한다.
- 현행 직렬 실행 방식과 계획 리뷰 개선의 비교 결과는 미측정으로 남아 있다.

평가 과정에서 빌드와 핵심 테스트 85개는 통과했다. 이는 실제 호스트에서 전체 사이클의 안정성과 비용 효율을 검증했다는 뜻은 아니다.

이전 소형 합성 과제에 대해서는 vanilla도 100점을 받았고, Bouncer 1.5.4 전체 사이클이 입력과 캐시 읽기 처리량을 약 70~100배 사용했다는 기록이 있다. 이 수치는 현재 버전의 성능이나 요금 배수로 일반화할 수 없지만, 작은 작업에서 절차 비용을 확인해야 할 이유가 된다.

관련 근거: [위협 모델](threat-model.md), [설치 문서](install.md), [파일럿 기록](../benchmarks/tasks/fastify-001-pilot.md), [측정 결과](../benchmarks/drive-serial-4/results.md).

## 2. SDD 관점에서 수정한 판단

Bouncer는 원래 SDD, 즉 명세 중심 개발을 지향했다. 이 목적에서는 구현 속도뿐 아니라 무엇을 만들기로 합의했고, 구현이 그 합의를 어떻게 충족했는지가 중요하다. 따라서 명세 작성과 승인에 드는 비용을 모두 불필요한 절차로 볼 수는 없다.

현재 구조에는 SDD의 기반이 있다.

- task brief를 구현 판단의 기준으로 전달한다.
- 승인한 범위와 실행 중 변경을 구분한다.
- 브리프 해시와 리비전으로 어떤 명세를 기준으로 작업했는지 기록한다.
- 명세 변경을 리뷰하면서 모순과 버그 발생 가능성을 검토한다.
- finalize 이후에도 epic·blueprint·explain 문서를 남긴다.

논의 중 다음 두 가지 평가는 수정했다.

### 명세의 지속성

task 문서가 정리·삭제된다는 사실만으로 명세의 연속성이 약하다고 판단한 것은 과했다. epic·blueprint·explain에 장기적으로 필요한 의도·계약·변경 근거를 남긴다면, 실행용 문서를 정리하는 설계로 볼 수 있다.

남은 문서가 현재 동작과 계약을 충분히 설명하는지는 계속 확인할 항목이다.

### 명세 변경의 검토

명세 변경을 리뷰하면서 버그 위험을 미리 파악하는 기능은 이미 존재한다. 이를 파일 범위 통제로만 평가한 것은 해당 기능의 가치를 충분히 반영하지 못한 판단이었다.

구현 전에 요구사항의 모순과 변경 영향을 찾는 것은 SDD의 중요한 효용이다.

### 남는 질문

승인된 명세의 각 요구사항이 최종 구현에서 충족됐다는 근거를 얼마나 명확하게 연결하는가?

명세 변경 리뷰는 구현 전 위험을 찾고, 요구사항별 검증은 구현의 누락을 찾는다. 두 기능은 서로 보완한다. 파일 범위 준수와 테스트 실행만으로 명세의 의미적 충족까지 자동으로 보장할 수는 없다.

수정된 평가는 **SDD의 중요한 요소를 갖췄으며, 적용할 작업 규모와 비용 효율을 검증해야 하는 도구**다.

## 3. Superpowers와의 경쟁

“SDD를 도와주는 플러그인”이라는 설명은 제품 범주를 전달하지만, 선택 이유로는 부족하다.

Superpowers도 설계 승인, 계획 작성, 명세 준수와 코드 품질 리뷰, 완료 전 검증을 제공한다. 확인한 실행 스킬에는 작업 원장과 재개 절차도 있다. 따라서 명세 작성·리뷰·기록 자체를 Bouncer만의 기능으로 내세우기는 어렵다.

참고: [Superpowers README](https://github.com/obra/superpowers), [실행 스킬](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [완료 전 검증 스킬](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md).

초기 포지셔닝 제안은 다음과 같았다.

> Bouncer — 승인한 명세에서 검증된 커밋까지 이어주는 SDD 플러그인.

그 선택 이유는 승인 범위, 실제 검증 기록, 검증 이후 소스 상태, 저장소에 남는 변경 근거였다. 이는 Bouncer라는 이름의 “무엇을 통과시킬지 판단한다”는 의미와도 연결된다.

다만 CLI 검사가 명세의 의미적 충족까지 보장한다고 홍보해서는 안 된다. 고의적 우회와 원장 위조를 막는 보안 경계로도 표현하지 않는다.

## 4. 병렬 task 실행을 반영한 포지셔닝

사용자가 지목한 핵심 기능은 task를 병렬로 처리할 수 있다는 점이다. 이는 승인·검증에 집중한 초기 평가에서 충분히 반영하지 못했던 가치다.

Bouncer가 제공하는 흐름은 다음과 같다.

1. 승인한 task DAG에서 병렬 실행할 작업을 고른다.
2. worker마다 별도 worktree에서 구현·검증한다.
3. 결과를 integration worktree로 모은다.
4. 통합 결과를 검증하고 blueprint 단위로 마감한다.

사용자가 얻는 가치는 여러 에이전트를 동시에 실행하는 기능뿐 아니라, 명세에 따라 나눈 작업을 병렬로 처리하고 그 결과를 검증하며 통합하는 흐름에 있다.

이를 반영한 브랜딩 제안은 다음과 같다.

> **Bouncer — 승인한 명세를 병렬로 구현하고, 검증된 결과로 통합하는 SDD 플러그인.**

보조 설명:

> 명세 변경을 리뷰하고, 독립된 task를 병렬로 실행하며, 승인 범위와 실제 검증 근거를 확인해 결과를 통합합니다. 변경의 의도와 설명은 저장소에 남깁니다.

| 요소 | 사용자에게 제공하는 가치 |
| --- | --- |
| SDD | 무엇을 만들지 합의하고 변경 영향을 검토한다. |
| 병렬 task 실행 | 독립된 작업을 동시에 처리해 대기 시간을 줄일 기회를 만든다. |
| 개별·통합 검증 | 각 작업과 합쳐진 결과의 검증 근거를 확인한다. |
| 지속되는 문서 | 후속 변경에서 의도와 판단 근거를 다시 사용할 수 있게 한다. |

병렬 실행의 시간 절감은 측정해야 한다. 작업 분할, 의존성, 통합 비용에 따라 이득이 달라지고 총토큰은 늘 수 있다.

“Superpowers에는 병렬 기능이 없다”거나 “Bouncer만 병렬 SDD를 제공한다”는 주장은 확인되지 않았다. 비교의 초점은 계획된 병렬 실행부터 통합 검증까지 얼마나 일관되게 제공하는가에 둔다.

## 5. 우선 대상 사용자

첫 대상은 **기존 코드베이스에서 여러 모듈에 걸친 변경을 독립된 task로 나눠 위임하고, 승인 범위와 통합 검증 근거를 확인해야 하는 개발자·팀**이다.

| 상황 | 현재 판단 |
| --- | --- |
| 작은 버그 수정·빠른 실험 | 전체 절차의 비용이 이득을 넘을 수 있다. |
| 요구사항 합의와 후속 변경 근거가 중요한 작업 | SDD 구조를 사용할 이유가 있다. |
| 독립된 task가 여러 개 있는 변경 | 병렬 실행과 통합 검증의 가치를 확인하기 좋은 대상이다. |
| 팀 전체의 기본 개발 절차 | 설치 안정성과 비용·효과 측정 이후 판단한다. |

Superpowers 전체보다 유명해지는 것을 먼저 목표로 삼기보다, 이 대상 사용자에게 Bouncer를 선택할 구체적인 이유를 제공한다.

## 6. 브랜딩을 뒷받침할 증거와 제품 과제

### 하나의 작업으로 전체 흐름을 보여주기

대표 사례에는 명세 변경 리뷰에서 발견한 문제, task 분할과 병렬 실행, 승인 범위 검사, 실제 검증, 통합 검증, 최종 epic·blueprint·explain을 포함한다.

게이트 번호나 coordinator 구조보다 사용자가 어떤 문제를 피하고 어떤 결과를 얻었는지 먼저 설명한다.

### 순차·병렬 비교

동일한 명세와 구현·검증 조건에서 Bouncer의 순차·병렬 경로를 비교한다.

- 최종 결과의 정확성과 요구사항 충족
- 벽시계 시간
- 총토큰과 측정 가능한 비용
- 통합 실패와 재작업
- 사람의 개입 횟수

### Superpowers 비교

같은 명세·모델·작업 조건에서 요구사항 누락, 범위 이탈, 오래된 검증 근거, 개입과 비용을 비교한다. 인위적인 위반을 게이트가 잡는 시연과 자연스러운 작업에서 사고를 줄이는 실험은 구분한다.

### 도입 장벽 줄이기

- README와 설치 문서의 경로를 일치시킨다.
- 실제 호스트에서 설치와 전체 사이클을 검증한다.
- 작은 작업에는 적절한 절차 비용을 제공한다.
- 기존 명세·계획을 가져오는 경로를 검토한다.

Superpowers와의 병용·계획 가져오기는 향후 검토 제안이다. 현재 호환성이 검증됐다는 뜻은 아니며, 제공한다면 승인·실행·커밋의 책임이 충돌하지 않는지 확인해야 한다.

## 7. 논의의 최종 방향

Bouncer는 **SDD를 제품 범주로 삼고, 승인된 명세에 따른 병렬 구현과 검증된 통합 결과를 선택 이유로 삼는 방향**이 적합하다.

현재 구조에는 그 방향을 설명할 기반이 있다. 다음 과제는 기능 수를 늘리는 것보다 설치 신뢰도, 요구사항과 검증 근거의 연결, 병렬 실행의 시간·비용·품질을 실제 사례로 증명하는 것이다.
