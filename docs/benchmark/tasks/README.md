# 벤치마크 태스크 명세

**측정일: 2026-08-21 (KST)**
**베이스 커밋: `3f5201866b368a55baaae845981ab77b9b869bec`** (`develop`, PR #52 머지 직후)

이 디렉터리는 A/B 에 사용한 태스크 4개의 정본이다. 각 태스크는
`references/task-suite.md` 가 요구하는 세 가지를 갖춘다 — 고정된 베이스 커밋,
**모든 arm 에 토씨 하나 안 바꾸고 주어진 프롬프트**, 에이전트에게 묻지 않고
심사자가 확인할 수 있는 완료 조건.

`prompt` 필드만 에이전트에게 전달했다. `done_when` 과 `probe` 는 심사자용이며
구현 에이전트는 보지 못했다. 양쪽 arm 이 같은 프롬프트를 받았으므로
"테스트를 추가하라" 가 프롬프트에 없다는 사실은 두 arm 에 동일하게 적용된다.

## 태스크 선정 기준

`task-suite.md` 의 표에서 서로 다르게 실패하는 네 가지 형태를 골랐다.
전부 이 저장소 자신의 코드를 대상으로 한다 — 합성 저장소를 쓰면
"그럴듯한 코드" 를 쓰는 에이전트가 유리해지고, 그건 이 벤치마크가 잡으려는
바로 그 실패다.

| id | 형태 | 무엇을 보려고 넣었나 |
| --- | --- | --- |
| t1 | 기존 코드에 작은 기능 | 가장 흔한 경우. 기존 helper 를 재사용하는가, 두 번째 경로를 만드는가 |
| t2 | 리포트 기반 버그 수정 | 리포트에 적힌 예시만 맞추는가, 결함의 클래스를 고치는가 |
| t3 | 동작 불변 리팩터링 | 스코프 규율이 살거나 죽는 자리 |
| t4 | 모호한 요구 | 되묻는가 / 가정을 크게 적고 진행하는가 / 조용히 추측하는가 |

의도적으로 **넣지 않은 형태**가 둘 있다. 3개 이상 모듈에 걸치는 변경과
"이미 있는 helper 를 재사용해야 하는" 중복 유도 태스크다. 둘 다 한 사이클이
길어져 이번 예산에 안 들어갔다. 다음 회차에 넣어야 n 이 스킬 권장치(5–8)에
도달한다.

## t1 — `bouncer verify --dry-run` (기능 추가)

**요구:** `bouncer verify --blueprint <dir> --dry-run` 이 검증 명령을 실행하지
않고, 해결된 verify 명령과 그 출처(task 문서 선언 / `.bouncer/config.json`)를
출력한 뒤 종료 0. `verification.md` 는 건드리지 않는다. 명령이 유효하지 않으면
`--dry-run` 없는 실행과 같은 실패 코드로 실패한다.

**함정:** 명령 해결 로직(`readVerifyCommand`)은 이미 존재하고, 포인터 task 문서
우선 → `config.verify` 폴백이라는 미묘한 우선순위를 가진다. dry-run 을 위해
두 번째 해결 경로를 새로 짜면 두 경로가 조용히 어긋난다. 재사용이 정답이다.

**측정 결과:** off 는 기능 자체는 정확히 구현했으나(correctness 5) **테스트를
0줄** 추가했고, `isCanonicalBlueprintDir` 가드를 복사-붙여넣기 했다(fit 3).
on 은 같은 기능에 테스트 135줄 + `docs/cli.md` 갱신까지 했다. **83.19 → 95.19**

## t2 — verify 명령의 셸 확장 차단 (버그 수정)

**요구:** `VERIFY_COMMAND_FORBIDDEN` 이 백틱·`$(`·체이닝 문자는 막지만
`$VAR` / `${VAR}` 는 통과시킨다. 이 명령은 `execSync` 로 셸을 거쳐 실행되므로
확장이 남아 있으면 게이트가 실제로 무엇을 돌렸는지가 환경에 따라 달라지고,
`verification.md` 의 증적이 재현 불가능해진다. 양쪽(plan 시점 S12, 런타임
`VERIFY_COMMAND_INVALID`)에서 동일하게 거부되어야 한다.

**이 버그는 실재한다.** 합성이 아니라 베이스 커밋의 `verification.ts:74` 를
읽고 찾은 것이다. `docs/security.md` 가 커밋 가드의 한계를 성실히 나열하는
반면, 이 확장 구멍은 어디에도 적혀 있지 않다.

**함정:** 리포트가 예시로 든 것은 `$FLAGS` 와 `${FLAGS}` 두 개뿐이다. 그
둘만 막는 정규식을 쓰면 `$0 $1..$9 $@ $* $# $? $$ $!` 가 그대로 남는다 —
리포트가 서술한 재현 불가능성 문제를 똑같이 가진 같은 클래스의 입력이다.

**측정 결과:** 정확히 그 갈림이 나왔다.
- off: `/[&|;\`<>\n]|\$\(|\$\{|\$[A-Za-z_]/` — 예시 두 개는 막고 특수 파라미터는
  전부 통과. 테스트 0줄. 심사자가 revert 체크를 돌려 확인: 수정을 되돌려도
  696개 테스트 전부 통과.
- on: `/[&|;\`<>\n$]/` — `$` 자체를 차단해 같은 클래스 전부 커버. 런타임과 S12
  **양쪽 표면에 각각 테스트**를 붙였고, 되돌리면 정확히 그 두 테스트가 실패.

**85.59 → 99.99**

## t3 — `cli-current-command.ts` JSON 출력 통합 (리팩터링)

**요구:** 한 파일 안에서 5번 반복되는
``io.out(`${JSON.stringify({ ... }, null, 2)}\n`)`` 를 한 군데로 모은다.
외부 관찰 가능한 동작은 완전히 동일해야 한다 — 출력 바이트, 종료 코드,
stderr 전부.

**함정:** "정리하라" 는 지시는 주변 파일(`cli-doc-commands.ts`,
`cli-project-commands.ts` 등 같은 패턴을 쓰는 형제 모듈)로 번지기 쉽다.
스코프 규율을 보는 자리다.

**측정 결과: 동점.** 양쪽 arm 모두 `emitJson` helper 하나를 만들고, 대상 파일과
그 빌드 산출물만 건드렸다. 심사자들이 베이스 커밋과 플래그 조합 5~7개의
stdout/stderr/종료 코드를 바이트 단위로 대조해 동일함을 확인했다. 양쪽 다
테스트를 추가하지 않았고(리팩터라 기존 스위트로 충분), 양쪽 다 **"바이트
동일" 이라는 이 태스크의 핵심 불변식을 잠그는 테스트는 없다**는 같은 지적을
받았다. **95.19 → 95.19 (Δ 0.00)**

이 동점이 이번 실험에서 가장 정직한 데이터다. Bouncer 를 켜도 안 움직이는
영역이 있다는 뜻이고, 그게 하필 README 가 첫 번째로 내세우는 "범위가 번진다"
영역이다.

## t4 — "verify 가 오래 걸리면 알려줘" (모호한 요구)

**프롬프트 전문:** `verify 가 오래 걸리면 사용자가 알 수 있게 해줘.`

명시하지 않은 것: **임계값, 출력 채널, 설정 키, 느린 verify 를 실패로 볼지
여부.** 에이전트에게는 물어볼 사람이 없다고 알렸다.

**숨은 함정:** verify 경로는 blocking `execSync` 다. 메인 스레드의 이벤트
루프가 명령이 끝날 때까지 멈추므로, `setTimeout` / `setInterval` 기반 구현은
**실행 중에 절대 발화하지 않는다** — 명령이 끝난 뒤에야 밀린 타이머가 돈다.
동작하는 답이 되려면 별도 스레드나 프로세스가 필요하다. 코드를 읽기만 하고
넘어가면 "구현했다" 고 보고하지만 실제로는 아무 신호도 안 나오는 답이 나온다.

**측정 결과:** 양쪽 다 이 함정을 통과했다. 둘 다 되묻지 않고 진행했다(물어볼
대상이 없었으므로 예상된 행동).

- off: detached 자식 프로세스 + 5초 간격, 되돌릴 수 없는 env var
  `BOUNCER_VERIFY_NO_HEARTBEAT` 추가. **테스트 0줄.** 심사자가
  `npm run test:coverage` 를 직접 돌려 **레포 자신의 CI 게이트가 깨짐**을 확인
  (function coverage 95.98% < 임계 96%). blocking finding 으로 기록되어
  **35.0 / F 로 실격.**
- on: `worker_threads` + `fs.writeSync(2, ...)`. 기본 30초, 주입 가능한 옵션.
  worker 의 일반 stdio 배관은 `execSync` 가 풀릴 때까지 flush 되지 않는다는
  점까지 실제 자식 프로세스 테스트로 증명하고 fd 직접 쓰기로 전환했다.
  가정(30초 기본값, 신호만 보내고 실패시키지 않음)을 주석에 명시. **92.79 / A**

**35.0 (실격) → 92.79.** 스킬 지침에 따라 실격 런은 평균에 섞지 않고 별도로
보고한다.

## 이 태스크 세트의 한계

- **n=4.** 스킬 권장은 5–8 이다.
- **셀당 반복 1회.** 태스크별 분산을 측정하지 못했다. t3 의 동점이 진짜 동점인지
  노이즈인지 구분할 수 없다.
- **태스크를 사람이 설계했다.** `task-suite.md` 는 병합된 실제 PR 에서 뽑으라고
  권한다. t2 만 실제 코드에서 발견한 버그이고 나머지 셋은 설계된 것이다.
- **크로스 커팅 변경(3개 이상 모듈)과 중복 유도 태스크가 빠졌다.** 에이전트가
  가장 흔히 무너지는 두 형태다.
