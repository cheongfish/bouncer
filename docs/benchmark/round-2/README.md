# 2회차: 강화 게이트 기준선 vs scaffold 개선 on-arm

1회차 표와 `docs/benchmark/runs/`는 그대로 둔다. 이 디렉터리는 Task 001 기준선(`c7df084`)과 Task 002~004 이후 HEAD(`6101b2b`)의 on-arm만 나란히 놓고, 1회차 off와 겹치는 축만 판정한다.

근거: [baseline.md](baseline.md), [improved.md](improved.md). 설계 통제는 [../protocol.md](../protocol.md).

## 성공 조건 판정 (n=4)

목표 네 줄은 에픽이 적어 둔 숫자다. 표본 4개로 “힌트 때문에”라고 인과를 닫지 않는다.

| 조건 | 쓰는 비교 | 관측 | 판정 |
| --- | --- | --- | --- |
| 시간 배수 ≤ 2.5 | 개선 on `wall_s` 합 1460s (24.33분) / 1회차 off 합 8.7분 | **2.80×** | **미달** |
| test quality Δ = +3.00 | 개선 on 평균 3.25 − 1회차 off 평균 1.50 | **+1.75** | **미달** |
| on 실격 = 0 | 개선 4런 블로킹 파인딩 0, 합성 캡 없음 | **0** | **충족** |
| G18/S9/G4 = 0 | 개선 4런 plan/execute 로그 | **0 / 0 / 0** | **충족** |

1회차 on의 test quality 평균은 4.50(+3.00)이었다. 이번 개선 on은 3.25다. 같은 네 프롬프트라도 구현·심사 세션이 바뀌면 차원이 이만큼 움직인다.

시간 배수는 1회차 off 벽시계만 분모로 쓴다. Task 001 기준선은 에이전트 벽시계를 표본에서 뺐다(CLI ~3s). 그 열과 이번 `wall_s`를 나눠 “기준선 대비 배속”을 만들지 않는다.

## 합성 · 차원

독립 블라인드 합성(측정 40 + 심사 60).

| task | 1회차 off | 2회차 기준선 on (`c7df084`) | 2회차 개선 on (`6101b2b`) |
| --- | ---: | ---: | ---: |
| t1 | 83.19 (B) | 95.19 (A) | 95.19 (A) |
| t2 | 85.59 (B) | 92.79 (A) | 89.47 (B) |
| t3 | 95.19 (A) | 90.39 (A) | 87.99 (B) |
| t4 | 35.0 (F, 실격) | 79.87 (C) | 75.07 (C) |
| 평균 (t4-off 실격은 1회차 README처럼 평균에 안 섞음) | off 정상 3개 87.99 | 89.56 | 86.93 |

test quality (0–5):

| task | 1회차 off | 2회차 기준선 on | 2회차 개선 on |
| --- | ---: | ---: | ---: |
| t1 | 1 | 4 | 4 |
| t2 | 1 | 4 | 4 |
| t3 | 3 | 2 | 2 |
| t4 | 1 | 4 | 3 |
| 평균 | **1.50** | 3.50 | **3.25** |

개선 on − 1회차 off = +1.75. 목표 +3.00이 아니다. 기준선 on 평균 3.50보다 0.25 낮다. n=1/셀이라 노이즈와 구별하지 못한다.

## 비용

| | 1회차 off | 1회차 on | 2회차 기준선 on | 2회차 개선 on |
| --- | ---: | ---: | --- | ---: |
| 토큰 합 | 202,268 | 442,061 | 없음 (제외) | 없음 (제외) |
| 툴콜 합 | 65 | 259 | CLI 스텝 13×n (제외) | 356 (`tool_calls_est`) |
| 벽시계 합 | 8.7분 | 28.8분 (3.32×) | CLI ~3s/런 (제외) | 24.33분 (**2.80×** vs off) |
| collect_s 평균 | (1회차 메트릭에 명령 시간이 있으나 벽시계 축이 아님) | | 4.46 | 6.21 |

개선 on의 툴콜 356은 구현 에이전트가 센 호출 수다. 1회차 65/259와 집계 방법이 다를 수 있어 배수 판정에는 쓰지 않았다. 시간 판정만 1회차 off 벽시계를 분모로 한다.

계획 문서(`.bouncer/context`, 런당 7파일):

| | 1회차 on | 2회차 기준선 | 2회차 개선 |
| --- | ---: | ---: | ---: |
| 줄 수 | 350 / 313 / 340 / 365 | 225 / 219 / 215 / 217 | 266 / 278 / 252 / 256 |

scaffold 힌트 이후에도 계획 7파일은 그대로다. 줄 수는 1회차보다 줄고 기준선보다는 늘었다. 작성자가 채운 본문 길이 차이이지 파일 수가 줄지는 않았다.

## 섞인 변수

같은 네 프롬프트·같은 검증 argv·같은 블라인드 심사 규약이어도 아래가 한 열에 겹친다.

- **베이스.** 1회차 `3f52018`, 기준선 `c7df084`(PR #53), 개선 `6101b2b`(002~004).
- **모델.** 1회차 Sonnet, 2회차 두 표본 모두 Grok 4.6. 1회차 off 대비 test quality·시간 Δ에 모델이 들어 있다.
- **구현 방식.** 기준선은 한 세션이 네 clone에 구현을 적용한 뒤 CLI 사이클만 재서 에이전트 비용을 제외했다. 개선은 클론마다 구현 에이전트 1명이다.
- **심사 세션.** 기준선 run-P/Q/R/S와 개선 run-J/K/L/M은 다른 심사자다. 합성 차에는 심사 분산이 있다.
- **n=4, 셀 반복 1.** t3 test quality 2는 기준선과 개선이 같다. 동점인지 노이즈인지 이 설계로는 모른다.

## 읽기

충족된 것은 실격 0과 G18/S9/G4 0이다. 시간 2.80×와 test quality +1.75는 적어 둔 목표를 못 채운다. 1회차 README가 내세운 test quality +3.00은 이번 개선 표본에서 재현되지 않았다.
